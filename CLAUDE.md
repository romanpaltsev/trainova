# CLAUDE.md — Дневник тренировок

## Проект

«Дневник тренировок» — адаптивное веб-приложение-дашборд для записи силовых и кардио-тренировок (зал, велосипед, бег, лыжи). Личный инструмент автора и учебный проект по Django; пользователи — автор и приглашённые друзья/родственники. Интерфейс на русском. Это pet-проект одного разработчика: простота и поддерживаемость важнее «энтерпрайзности».

Имя **Trainova** (репозиторий github.com/romanpaltsev/trainova) — рабочее: им подписан ярлык на рабочем столе, но окончательное название ещё не выбрано, и его сменят. Поэтому имя ярлыка живёт ровно в двух местах — `apple-mobile-web-app-title` в `templates/_page.html` и `name`/`short_name` в `templates/manifest.json` (плюс тест `test_home_screen_name_is_trainova`); переименование — правка этих трёх строк. В интерфейсе, письмах и текстах продукт называется «Дневник тренировок»: короткое латинское имя нужно там, где подпись под иконкой обрезается, а не в текстах.

## Стек (зафиксирован — не менять и не предлагать альтернатив)

- Python 3.12+, Django (актуальный стабильный релиз)
- Зависимости и окружение — uv: pyproject.toml + uv.lock (lock-файл коммитится), `uv sync` / `uv run`; pip напрямую не использовать, requirements.txt не заводить. Dockerfile ставит зависимости тоже через uv
- Серверный рендеринг: шаблоны Django + HTMX; Alpine.js для мелкого клиентского интерактива (таймер, модалки)
- Chart.js для графиков
- PostgreSQL, psycopg 3
- django-allauth для аутентификации
- Тесты: pytest + pytest-django + factory_boy. Линт/формат: ruff
- Docker Compose для разработки: web + postgres + mailpit
- Секреты через .env (django-environ); .env не коммитится, .env.example всегда актуален
- UI-основа — Bootstrap 5.3+ (без jQuery); поверх него свой `static/css/tokens.css` с фирменными цветами и переопределением переменных Bootstrap
- JS/CSS-библиотеки (Bootstrap, HTMX, Alpine, Chart.js) хранить локально в static/ (vendored), без CDN
- Tailwind, AdminLTE и другие UI-слои не использовать
- НЕ использовать: DRF, React/Vue/SPA, celery/redis

## Ключевые архитектурные решения

1. **Кастомный пользователь**: `accounts.User(AbstractUser)`, создан ДО первой миграции, `AUTH_USER_MODEL = "accounts.User"`.
2. **Auth-флоу (allauth)**: регистрация email+пароль, обязательное подтверждение email, вход по email (без username), восстановление/сброс/смена пароля. Без соцлогинов. Honeypot-защита от ботов на форме регистрации.
3. **Почта**: все SMTP-настройки из env; в dev — mailpit. Код не зависит от конкретного бэкенда почты.
4. **Модель данных** (приложение `workouts`):
   - `Sport`: name, category ∈ {strength, cardio}, owner (FK User, NULL = глобальный)
   - `Exercise`: name, muscle_group (необязательное; у своих упражнений задаётся при создании и правится на странице упражнения — чипы уже используемых групп плюс своё значение, написание приводится к уже принятому, чтобы не появились «Грудь» и «грудь»; список групп строится из данных, без choices), owner (FK User, NULL = глобальное), measurement ∈ {weight_reps, reps, time, time_weight} — в чём считается подход; по умолчанию «вес × повторы», у планки — время
   - `Location`: owner (FK User, **обязателен** — глобальных мест не бывает), name, is_default — **личный справочник мест тренировки**: зал, дом, маршрут — одна сущность на всё, поля-типа нет (различие «зал или заезд» выражается поведением, а обязательный выбор типа противоречил бы созданию на ходу). Не наследник `CatalogItem`: nullable owner, второй индекс «на глобальные имена» и `is_global` были бы мёртвым кодом. Место создаётся вводом нового названия (`services.location_for_name` — контракт `ExerciseQuickForm.save_for_user`: совпадение имени значит «это оно», а не ошибку дубля; регистр не важен, написание возвращается вместе с найденной записью), **первое место сразу становится дефолтным** — иначе молчаливая подстановка молчала бы, пока не заглянешь в профиль. Место **переименовывается** — ради этого оно и модель, а не текстовое поле: опечатка правится один раз и чинится по всей истории. Дефолтов не больше одного на владельца: частичный `UniqueConstraint unique_default_location_per_owner`; **менять его можно только двумя UPDATE'ами** («снять у всех», потом «поставить одному») под `select_for_update` — частичный уникальный индекс в Postgres проверяется немедленно и построчно, а `deferrable` вместе с `condition` Django запрещает
   - `Workout`: user, sport, location (nullable FK Location, PROTECT — NULL = место не указано: так записана вся история до появления справочника, бэкфилл невозможен и был бы выдумкой; силовая берёт место по умолчанию молча — и при старте, и при «Повторить», потому что повтор значит «сделать то же сегодня», а не «скопировать запись»; кардио спрашивает место в форме; сменить можно на экране тренировки и **в итоге записанной** — экрана правки силовой нет, и иначе забытое место осталось бы неисправимым), started_at (nullable — NULL = черновик: тренировка подготовлена заранее, время не идёт), duration_min (NULL = тренировка не записана: либо идёт, либо ещё не начата), note, rest_seconds (nullable — отдых между подходами для ЭТОЙ тренировки; NULL = значение по умолчанию из профиля `User.rest_seconds_default` (90 сек); изменение длительности отдыха на экране живого режима записывается сюда и действует до конца тренировки), current_exercise (nullable FK Exercise — выбранное вручную текущее упражнение живого режима); для силовых длительность считается живым режимом, для кардио вводится руками
   - **Три состояния тренировки выводятся из этих двух колонок, отдельного поля-статуса нет**: черновик (`started_at IS NULL`) → идёт (`started_at NOT NULL`, `duration_min IS NULL`) → записана (`duration_min NOT NULL`). Черновиков может быть сколько угодно (план на пн/ср/пт), идущая — не больше одной на пользователя: частичный `UniqueConstraint unique_live_workout_per_user`. Комбинация «записана, но не начиналась» запрещена `CheckConstraint finished_workout_is_started`, поэтому `.finished()` гарантирует непустой `started_at` и `localtime(started_at)` в истории и агрегатах не может подставить `now()` вместо настоящей даты. `Meta.ordering` использует `nulls_last`: иначе Postgres поставил бы черновики в начало любой выборки без явной сортировки. Фильтровать только методами `Workout.objects.finished() / live() / planned() / unfinished()`
   - `StrengthSet`: workout, exercise, set_number, weight_kg (Decimal), reps, duration_sec (секунды удержания), measurement (снимок единицы упражнения на момент записи — смена единицы не переписывает историю; неприменимые поля обязаны быть нулём, это держит CheckConstraint `set_fields_match_measurement`, и благодаря ему тоннаж `Sum(вес × повторы)` верен без фильтров), done (False = плановый подход живого режима; при завершении тренировки невыполненные удаляются — в завершённой тренировке остаются только выполненные), done_at (когда нажали «Подход выполнен»; NULL = либо подход плановый, либо он записан до появления поля — бэкфилл невозможен, времени выполнения в старых данных нет). **Порядок упражнений в тренировке считается по `done_at`, а не по порядку добавления**: `models.exercise_order_key` сортирует группы по паре «самая ранняя метка упражнения или бесконечность, затем `min(id)` подходов», поэтому в итоге получается фактический порядок, в очереди живого режима — план, а тренировка без меток ведёт себя как раньше. Метку пишут ровно два места — `SetDoneView` ставит, `SetUndoView` очищает (у невыполненного подхода её быть не может, это держит CheckConstraint `set_done_at_only_when_done`); из-за этого удаление невыполненных подходов при завершении больше не может сдвинуть порядок. Номер упражнения — позиция в этом отсортированном списке, кладётся в `group["position"]` в `services.exercise_groups` и в `stats.exercise_positions`: `forloop.counter` в шаблоне не годится, живой экран разрезает список на «сейчас / дальше / выполнено» и счётчик дал бы в каждом разделе свою единицу. **Подпись силовой тренировки выводится из подходов, а не из имени вида спорта**: слово «Силовая» одинаково у всех, и лента истории превращалась в столбец одинаковых строк, поэтому в заголовке стоят группы мышц этой тренировки — `stats.muscle_groups_by_workout` (третий и последний потребитель `exercise_order_key`, порядок групп обязан совпасть с порядком упражнений в итоге), две группы плюс `+N`. Считается агрегатом на всю страницу и раскладывается по объектам `stats.attach_muscle_groups`, а не свойством модели: свойство читало бы подходы у каждой карточки и делало ленту N+1 (это стережёт `test_history_query_budget` — 9 запросов и при двух неделях истории, и при восьми). Фолбэк на `sport.name` живёт в шаблоне (`{{ workout.muscle_groups|default:workout.sport.name }}`), поэтому забытая точка вызова даёт прежнюю подпись, а не пустоту; у кардио групп не бывает, и там всегда имя вида спорта. Живой экран подписью не пользуется — заголовок достраивался бы прямо по ходу тренировки
   - `ExerciseNote`: workout, exercise, text (до 500 символов) — заметка к упражнению внутри тренировки («болело плечо», «узкий хват»); одна на пару (UniqueConstraint), «заметки нет» = строки нет (пустой текст удаляет запись); `exercise` удаляется CASCADE, а не PROTECT как у подхода — иначе осиротевшая заметка сделала бы личное упражнение неудаляемым без способа её убрать; пишется в живом режиме и в черновике, в записанной тренировке только читается; в следующей тренировке показывается подсказкой «заметка в прошлый раз» из той же тренировки, что дала подстановку весов
   - `ExerciseSettings`: user, exercise, weight_step — **настройки упражнения у конкретного пользователя**, дом для будущих настроек: новые добавляются полями сюда, а не в `Exercise`. Почему отдельная модель: глобальные упражнения правит только админ, а шаг веса у приседа со штангой каждый настраивает под свой зал (у приглашённых друзей — свой). Строки нет = действуют умолчания (`DEFAULT_WEIGHT_STEP` 2,5 кг), она появляется при первом изменении; `exercise` удаляется CASCADE, как у заметки. Шаг подмешивается к подходам и упражнениям аннотацией `with_weight_step` — отдельный запрос на упражнение сделал бы живой экран зависимым от их числа
   - `CardioDetails`: OneToOne(Workout), distance_km (Decimal), avg_heart_rate (nullable)
   - `ChangelogEntry`: kind ∈ {feature, fix}, title, body, published_at (редактируемая — можно ставить задним числом и отложенно), is_published — новости проекта («Что нового»); анонс пользовательской доработки едет вместе с ней одноразовой data-миграцией (`get_or_create` по заголовку, дата зашита) и пишется языком пользователя, а не разработчика; в `seed` — только стартовые записи для пустой базы; правит и снимает с публикации админ через Django admin; менеджер даёт `published()` и `unread_for(user)`; у `User` поле `changelog_seen_at` (NULL = ещё не открывал) — страница «Что нового» при открытии обновляет его, пункт в профиле показывает точку-бейдж, если есть опубликованные записи новее
5. **Гибридные справочники** (Sport, Exercise): записи с owner IS NULL — глобальные, правит только админ через Django admin; пользователь видит глобальные + свои: `Q(owner__isnull=True) | Q(owner=user)`. Уникальность имени — в пределах владельца (UniqueConstraint с учётом NULL).
6. **Изоляция данных — священное правило**: каждый queryset пользовательских данных фильтруется по request.user; чужая запись по прямому URL — 404. На каждую вьюху с данными — тест «пользователь А не видит данные Б».
7. **Никакой социальности**: пользователи не видят друг друга ни в каком виде.
8. **Живой режим и черновик — один экран и один URL** (`workout_live`): различие только в `started_at`, поэтому после кнопки «Начать тренировку» адрес не меняется и открытая вкладка остаётся рабочей. Степперы отвечают мгновенно: значение меняется на тапе (правила приходят в data-атрибутах из `SET_STEPS`/`SET_LIMITS`), а ответ сервера его подтверждает — это осознанное исключение из «форматирует всегда сервер». У htmx задан `timeout` (meta `htmx-config` в `_page.html`): без него повисший на мобильной сети запрос навсегда блокировал очередь `hx-sync`, и значение застывало до перезагрузки; при обрыве значение помечается «не сохранено». Черновик правится теми же эндпоинтами живого режима (добавить упражнение, степперы, убрать подход); запрещены только те действия, которые требуют идущего времени: «Подход выполнен» и «Завершить» отдают 404.

## UI-конвенции

- Один адаптивный дизайн, mobile-first: базовые стили под ~375px, брейкпоинты (min-width) вверх до полноценных десктопных раскладок — они есть у всех экранов, не только у дашборда (см. «Десктоп» ниже).
- Главный сценарий — телефон в спортзале: тач-таргеты ≥ 44px, крупные кнопки шага веса (шаг задаётся у каждого упражнения на его странице: у штанги 2,5 кг, у гантелей 0,5 кг; повторы и время шагают общими 1 и 15 с), `inputmode="decimal"/"numeric"` на числовых полях, минимум набора с клавиатуры. Тап по значению подхода открывает ввод руками (кнопки шага на это время скрыты), значение разбирает сервер: вес принимает «82,5» и «82.5», время — «1:30» и «90».
- **Темы**: светлая и тёмная через color modes Bootstrap — атрибут `data-bs-theme` на `<html>`. Фирменные цвета — CSS custom properties в `static/css/tokens.css`, определённые для обеих тем (через переменные Bootstrap или свои `--app-*`-токены). Хардкод цветов в стилях и шаблонах запрещён — только переменные. Переключатель в шапке; дефолт — prefers-color-scheme; выбор — в localStorage; анти-FOUC-скрипт инлайном в `<head>`.
- Каждая страница обязана корректно выглядеть в обеих темах и на 375px/1440px.
- PWA: manifest.json + иконки + theme-color. Service worker НЕ делать (офлайн вне скоупа).
- Русский интерфейс; единицы: кг, км, мин; удержания и отдых — «1:30» (`rest_display`). `TIME_ZONE = "Europe/Moscow"`, `USE_TZ = True`.

## Дизайн (эталон утверждён 25.08.2026)

- Визуальный эталон — макеты семи экранов (дашборд моб. и десктоп, живой режим, кардио-форма, история, профиль, «что нового»); PNG-экспорты лежат в `docs/design/`. Верстать по ним: компоновка, плотность, скругления, иерархия текста.
- Файлы `docs/design/*-desktop.png`, **кроме `dashboard-desktop.png`**, — не макеты дизайнера, а утверждённые скриншоты реализации: десктопных макетов для этих экранов не рисовали. Сверять с ними компоновку можно, но при расхождении с правилами ниже главнее правила.
- Тёмная тема — основная (как в макетах); светлая строится из тех же ролей токенов, ниже даны оба набора. Bootstrap-переменные (`--bs-body-bg`, `--bs-body-color` и т.п.) переопределяются из tokens.css под оба значения `data-bs-theme`.
- **Шрифты** (Google Fonts, woff2-файлы хранить локально в `static/fonts/`): Unbounded 600/700 — крупные числа и таймеры (утилитарный класс `.num`); Manrope 400–800 — весь остальной текст. Fallback: `system-ui, sans-serif`. Unbounded лежит одним сабсетом (`unbounded-subset.woff2`): в `.num` попадают только цифры, знаки и единицы вроде «кг», «повторов», поэтому штатные сабсеты Google качали 82 КБ ради букв, которых там не бывает. Набор символов взят с запасом — вся базовая кириллица, — так что новое слово внутри `.num` ничего не сломает; команда перегенерации записана в шапке `static/css/fonts.css`. Три реально нужных файла шрифтов предзагружаются (`rel="preload"` в `_page.html`), остальные сабсеты Manrope браузер не запрашивает.
- **Токены тёмной темы** (из макетов): фон `#0D1015`; карточка `#151A21`; приподнятая поверхность `#1B222B`; линия `rgba(255,255,255,.08)`; текст `#EDF1F7`, вторичный `#9AA5B5`, приглушённый `#77828F`; акцент `#C6F13E` (текст на акценте `#141A08`); успех/положительная дельта `#0ca30c`.
- **Токены светлой темы** (те же роли): фон `#F6F7F9`; карточка `#FFFFFF`; линия `rgba(15,23,32,.10)`; текст `#16202B`, вторичный `#5A6675`, приглушённый `#8A95A5`; акцент тот же `#C6F13E` с текстом `#141A08`; успех `#006300`.
- **Цвета видов спорта** (серии графиков; цвет закреплён за видом спорта, а не за порядком в наборе): тёмная тема — Силовая `#3987e5`, Велосипед `#d95926`, Бег `#199e70`, Лыжи `#c98500`; светлая — `#2a78d6` / `#eb6834` / `#1baf7a` / `#eda100`. Наборы проверены на различимость при дальтонизме на своих поверхностях. В графиках всегда легенда; числа и подписи — цветом текста, никогда цветом серии.
- **Правила графиков** (Chart.js настраивать под них): stacked bar с зазором 2px между сегментами и скруглённым верхом; тонкая сетка, подписи осей ≥11px приглушённым цветом; одна ось Y, без двойных осей; главный график дашборда — часы по неделям с разбивкой по видам спорта.
- **Прочее**: радиусы — карточки 16px, поля 12px, чипы/круглые кнопки pill (999px); иконки — только инлайн-SVG stroke 2px (никаких emoji в UI); у каждого вида спорта цветовая точка-маркер рядом с названием.

## Десктоп (768 / 1200)

- **Два брейкпоинта и никаких новых**: `@media (min-width: 768px)` (появляются верхняя навигация и CTA, исчезает нижняя) и `(min-width: 1200px)` (многоколоночные раскладки). Правки десктопа живут только внутри них — **мобильный вид неприкосновенен**, и это проверяется скриншотом 375px до/после.
- **Ширину задаёт страница, а не компонент.** `{% block main_class %}` ставит меру: `app-main-narrow` (26rem — подтверждения, смена пароля), `app-main-form` (34rem — формы и справочники), `app-main-read` (44rem — история и новости), `app-main-dual` (34rem → 70rem на 1200px — профиль, живой режим, итог), `app-main-feed`/`app-main-catalog` (свои раскладки на 1200px). Правило одно: `.app-main > * { max-width: var(--app-measure); margin-inline: auto }`. Не возвращать `max-width` компонентам — из-за этого один `.app-rows` тянул одну ширину в трёх разных раскладках.
- **Отступы и ширины — только токенами**: `--app-space-*` (шкала по 0.25rem), `--app-measure-*`, `--app-gutter` (1 → 1.5 → 3.5rem, один и тот же у шапки и `.app-main`, иначе на 1920px они расходятся). Предел страницы — `--app-measure-page` (1440px), по нему выровнена и шапка.
- **История на 1200px — плотные строки**: колонки задаёт список (`.app-feed`), карточки берут их через `grid-template-columns: subgrid`, поэтому цифры выравниваются через все недели без магических ширин. Всё под `@supports (subgrid)`. Состав метрик у силовой и кардио различается, поэтому колонки позиционные: 3-я — время, 4-я — «сколько», 5-я — «насколько интенсивно». Место и заметка **делят 6-ю колонку** (`.app-workout-meta`): своего трека месту не дают, потому что `max-content` зарезервировал бы его ширину во всех строках, а у истории до появления справочника места нет вовсе. На телефоне обёртка не образует бокса (`display: contents`), поэтому карточка рендерится как до фичи; на 1200px внутри колонки это один текстовый прогон с единственной точкой обрезки, а зазор даёт `margin`, а не символ-разделитель — тот остался бы висеть при обрезке. Классы в 1200-блоке перечислены явно, без `> *`: мобильное правило `.app-workout-meta > .app-place` весит два класса и перебило бы селектор с универсальным.
- **Справочник упражнений на 1200px — мастер-деталь**: `ExerciseDetailView` смотрит `HX-Request` и отдаёт `_exercise_detail_body.html` вместо страницы; отдельного URL у панели нет, чтобы проверка доступа осталась в одном месте. Клик перехватывается в JS: в htmx `preventDefault()` для клика по `<a>` срабатывает раньше фильтра события, поэтому `hx-trigger="click[matchMedia…]"` убил бы навигацию на мобильном. График после свопа пересобирается через `appCharts.destroy()` — иначе Chart.js падает на переиспользованном canvas. Левая колонка 30rem и **без внутренней прокрутки**: своя полоса торчала посреди экрана, а липкой колонку делать нельзя — залипший элемент выше вьюпорта перестаёт двигаться, и всё ниже кромки становится недостижимым. По той же причине липкая только шапка панели (`.app-exercise-head`), а не панель: у упражнения с двумя десятками тренировок она уходит на три экрана. Элементы списка общаются с JS через `data-exercise-item` / `data-exercise-link`, а не через классы: классы стилевые и меняются вместе с вёрсткой, а в мастер-деталь одинаково попадают и плитка, и строка. Порядок блоков на 1200px задаёт `order` у прямых детей `.app-exercise`, поэтому **новый блок обязан быть одной секцией со своим `order`**: заголовок и список по отдельности разъедутся по разным местам экрана. Сводка «По местам» (рекорд и число тренировок в каждом месте) считается в Python по уже загруженным подходам — `select_related("workout__location")` добавляет один LEFT JOIN в тот же запрос, поэтому бюджет 9 не двигается; показывается только при двух и более разрезах, «Место не указано» — такой же разрез, как остальные.
- **Каталог упражнений делится на два блока**: сверху «Я тренирую» — плитки упражнений с записанными тренировками (рекорд, число тренировок, дата последней, свежие первыми), ниже полный справочник по группам мышц. Признак — `workouts_count > 0`, **а не наличие рекорда**: метрика весовых упражнений это вес, поэтому у подтягиваний с собственным весом и у упражнения со сменённой единицей рекорда нет, а тренировок двадцать. Дата берётся вторым агрегатом на том же джойне (`Max("sets__workout__started_at", filter=…)`) — это ноль дополнительных запросов, а бюджет каталога упёрт в 7. Выполненное упражнение остаётся и в справочнике: иначе в «Груди» не оказалось бы жима лёжа. Один URL поэтому соответствует двум элементам, и подсветка выбранного зажигает оба — это следствие решения, а не дефект. При активном поиске или фильтре блок плиток скрывается: тогда нужен один список результатов.
- **Отделка описана один раз** в секции перед первым медиазапросом: `--app-transition-ui` (анимируем только цвет, фон, рамку, filter, тень и transform — никогда width/height/padding), hover целиком внутри `@media (hover: hover) and (pointer: fine)` (иначе на тапе подсветка залипает), фокус — `--app-focus-outline` через `:where(...)` с нулевой специфичностью. `prefers-reduced-motion` гасит токены движения, а не все переходы: у полосы таймера отдыха переход функциональный.

## Вне скоупа v1 — не делать и не предлагать «на вырост»

Соцфункции (лента, сравнение пользователей), импорт из Strava/Garmin/часов, многонедельные программы тренировок (циклы, переиспользуемые шаблоны «День A/B», отчёт «план vs факт»); подготовить одну конкретную тренировку заранее — можно и уже сделано, а вот программа на недели вперёд — нет. Настраиваемые виджеты дашборда, офлайн-режим/service worker, REST API, аналитика по группам мышц, соцлогины, мультиязычность, ник и загрузка аватарки (в v1 аватар — первая буква email, никаких файловых аплоадов и MEDIA).

## Рабочий процесс

- Автор учится Django: при нетривиальных решениях коротко объясняй «почему так» (1–3 предложения, без лекций).
- Одна фича за раз; после каждого этапа приложение в работающем состоянии.
- Тесты обязательны для: изоляции данных, гибридных справочников, подстановки прошлых значений (вес, повторы, время), агрегаций дашборда.
- После вёрстки каждого экрана — скриншоты через Playwright в 375px, 1024px, 1440px и 1920px в обеих темах; посмотри на них сам, сверь с `docs/design/` и поправь расхождения до сдачи этапа. 1024px и 1920px нужны потому, что между брейкпоинтами и за пределом 1440px раскладка ведёт себя иначе, чем на «круглых» ширинах.
- Миграции всегда коммитятся; `ruff check` и `ruff format` перед коммитом.
- Коммиты небольшие, сообщения на русском.

## Definition of Done для любой фичи

Работает в мобильном вьюпорте; pytest зелёный; обе темы целы; изоляция данных покрыта тестом; .env.example обновлён при новых настройках; нет захардкоженных цветов; новые отступы и ширины — только через `--app-space-*` / `--app-measure-*`; правки десктопной раскладки — только внутри медиазапросов, мобильный вид сверен скриншотом до/после.
